Treehammock Detailed Correction PR Plan
Ordered implementation specifications and finding closure requirements
Version 1 • October 3 2026 • Companion to Treehammock Correction Design
1 Scope and execution rules
Implement the correction design through 24 ordered PR specifications. Every one of the 52 findings recorded 
through R05 has exactly one primary owner in this plan. Shared prerequisites and cross-feature tests may span
multiple PRs, but each finding closes only when its observable acceptance criteria pass. The trusted-grant 
activation model is user selected. Other policy defaults are recommendations to be recorded in COR01 before 
dependent work.
This plan does not assert that the project is currently feature complete or that these are the last findings. R06 
through R10 still require their full review passes. COR01 establishes those review tasks, and COR23 reconciles 
their results. Any newly discovered defect must become a concrete correction PR before COR24 can qualify 
release. Unknown future defects are not labeled repaired by an umbrella work item.
All existing paths below are relative to the supplied repository root. Paths explicitly marked New are proposed 
additions. SQL changes must update versioned migrations and the canonical baseline, with executable 
equivalence checked for both current baseline files. Do not edit only a greenfield baseline and call an upgrade 
complete.
Every code PR includes its domain contract/documentation updates and relevant tests. No PR merges with 
deliberately failing default CI tests. A reproduction may use an isolated diagnostic lane before its owner fix, but
the closure test must be enabled in mandatory CI when the fix merges. Test fixtures must reproduce the real 
invariant; string-presence checks cannot replace SQL or cache execution.
2 Program order
COR01 establishes evidence, policy, review gates, and workload budgets. COR02 through COR06 provide 
database and coordination foundations. COR07 through COR10 repair authentication and proof authority. 
COR11 through COR18 repair recovery, delivery, factors, identity, and deletion. COR19 through COR21 
complete trusted activation. COR22 bounds maintenance and measured resource use. COR23 closes the 
remaining review scope through named corrective PRs as needed. COR24 qualifies the complete integrated 
release.
Dependencies are hard prerequisites unless a PR explicitly allows an earlier isolated correction. A listed finding 
may depend on a later integration PR for final closure; its ledger entry stays Open until that integration test 
passes. Parallel development can use these boundaries, but this document does not authorize deployment or 
introduce an agent delegation requirement.
3 Common validation lanes
Run from the repository root, using disposable databases and test-only provider accounts. These are existing 
script interfaces inspected in source; they have not been executed successfully in this review environment.
 Fast lane: bash eng/validate.sh --configuration Release --locked-restore. Includes locked restore, build, unit
and in-process integration suites.

COR04 Add durable operation outcomes and commit reconciliation
Findings owned: AUTH-02. Dependencies: COR02, COR03.
Problem and result: A request deadline currently stops waiting while a mutation can commit later. Make 
retries reconcile a durable operation before executing again.
Files: Repos/SessionRepo.cs and other security mutation repositories; middleware and controller guards; 
account/reset/factor service mutation methods. New: DataLayer/Operations/SecurityOperation.cs, 
Repos/SecurityOperationRepo.cs, Services/SecurityOperationService.cs and migration for operation receipts.
Implementation: Allocate operation identity before a mutation and bind it to scope, purpose-separated 
request HMAC, expected authority and version. In the same transaction, perform the mutation and store its 
safe outcome. On canceled/failed commit acknowledgment, use a separately bounded reconciliation read; 
distinguish pending, known committed, known rolled back, and unknown outcome. Return a retryable 
operation status without fabricating failure or automatically issuing another mutation. Observe eventual task 
failures. Reconciliation must remain authorized after ordinary token generation changes but must not deliver 
secret output after account/family revocation. Generic receipts contain no raw access token or setup seed.
Tests: Hold account lock beyond the request deadline then release; inspect rows and operation result. Drop 
the connection after commit but before acknowledgment. Retry the same operation through another instance.
Stop the process at each mutation/receipt boundary and verify no duplicate effect. Validate bounded pool/lock
occupancy and operation expiry.
Acceptance: Every affected mutation has a determinate replay/restart protocol; late commit cannot silently 
strand a client or be repeated as fresh work. A query timeout is never represented as proof of rollback. Secret￾specific refresh recovery is completed in COR09.
Migration and rollback: Add receipt table/indexes with bounded retention; deploy writer and reconciliation

receipts and fencing semantics.
