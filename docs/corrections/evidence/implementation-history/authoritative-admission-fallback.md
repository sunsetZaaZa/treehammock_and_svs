# COR23M — per-policy authoritative admission fallback

Date: 2026-10-09 (America/Chicago). Baseline: completed COR23L. Owner: R09-01, P2. Depends on COR03/COR05/COR08/COR12/COR23 and preserves COR23K provider health and COR23L startup prerequisites. Status: FixedPendingQualification; native qualification NotRun.

## Problem and resulting behavior

The old AllowWhenPostgreSqlAuthoritativeStateExists flag returned Allowed=true with count zero on cache failure without enforcing any equivalent SQL quota. Account lockout and proof-attempt rows do not enforce cross-account Login IP limits or hourly Delivery account/destination/IP quotas. Both cache and SQL could be unavailable while that flag still admitted expensive or delivery work.

FailClosed remains the default. The obsolete flag is replaced by RequirePostgreSqlBudgetV1 plus an explicit PostgreSqlFallbackPolicies selection. Each selected supported policy enforces a committed equivalent PostgreSQL budget before considering the cache, including when the cache is healthy. That continuous authority preserves history across outage and recovery; opening a new SQL counter only after Redis fails would grant another quota. Cache denial remains conservative. Cache failure can return only the already committed durable decision for that exact policy, dimension, identity, limit and window. Returned successful fallback has a positive authoritative count and no unavailable reason; infrastructure failure is recorded separately.

| Policy | Dimensions supported by SQL budget v1 | Cache failure behavior |
| --- | --- | --- |
| Login, explicitly selected | Account, IdentifierFingerprint, IpFingerprint | Allow only after an equivalent committed SQL admission; SQL failure/unknown completion denies. |
| Delivery, explicitly selected | Account, IdentifierFingerprint, IpFingerprint (channel remains in identity) | Same durable admission; account budget survives destination/IP rotation. |
| Login/Delivery not selected; unsupported dimensions | Cache policy only | Unavailable, deny; no SQL budget write. |
| TwoFactorChallenge, TwoFactorSetup | All current counter dimensions | FailClosed. Existing durable proof/setup limits remain independent. |
| PasswordResetRequest/TokenVerification/TwoFactorProof/Finalize | All current counter dimensions | FailClosed. Existing reset/proof authorities remain independent. |
| Signup, Reauthentication, AccountUnlock, AccountDeleteFinalize, PublicTokenVerification, Activation | All current counter dimensions | FailClosed; existing durable account/proof/create limits remain independent. |

The catalog explicitly supports the six Login/Delivery feature-dimension pairs. It never assumes that some existing row supplies an equivalent quota. Unsupported policies in PostgreSqlFallbackPolicies, duplicates, empty version-1 selection, undefined mode values, obsolete mode text and a nonempty selection under FailClosed are rejected by startup validation. Default profiles select no SQL policies. The example `deploy/abuse-budget-v1.example.json` is an overlay to merge deliberately through deployment configuration; it is not automatically loaded.

## Durable owner and admission algorithm

`abuse_admission_budgets_v1` holds policy/dimension integers, a fixed 32-byte SHA-256 identity digest, count, absolute window/cooldown expiry and indexed retention expiry. It stores no raw destinations/IPs/tokens and has no account/proof foreign keys. Identity derives from the existing normalized policy key, including channel and safe account/identifier/IP identity. Policy/dimension constraints and the SQL entry point independently reject unsupported inputs before allocation.

`cor23m_increment_budget_v1` uses an atomic unique-row upsert, retaining its row lock through the transaction. Server clock_timestamp is sampled after acquisition, so a waiting transaction cannot use its stale start time. A fixed window starts at first admission and never slides on subsequent attempts. Exact expiry uses <=. Count saturates safely; a call beyond the threshold starts configured cooldown. Active cooldown denies without incrementing and survives a shorter counter window. Cooldown/reset entry points use the same exact identity. Expiry cleanup and admission share row locking; the atomic upsert avoids a missing-row race with concurrent deletion.

The production PostgreSqlAbuseBudgetStore owns an independent bounded transaction for each admission/read/reset, disposes readers before commit and returns decisions only after confirmed commit. Statement/lock timeouts, the overall PostgreSqlBudgetTimeoutMilliseconds wait, caller cancellation and observed abandoned tasks bound dependency waits. SQL errors, lock/statement timeout, invalid results and commit uncertainty become explicit unavailable denial. A late transaction may consume budget; it cannot retroactively authorize work. There is no refund on Redis denial/failure, so uncertainty or partial multi-dimension admission may reduce availability conservatively. Multi-dimension requests are sequential, not one all-or-none transaction: earlier charges remain if a later dimension denies.

RequirePostgreSqlBudgetV1 and its policy set are snapshotted at counter-store composition. Selected requests consult SQL first; no cache/hash/provider work follows SQL denial. Healthy Redis is an additional brake. If both admit, the authoritative count is returned so cache outages cannot hide accumulated counts from downstream logic. Unselected/Redis-only policies keep the existing atomic cache algorithm and fail closed on failure. Durable reset must complete before cache reset; a failed/uncertain SQL reset never authorizes a cache clear. Resets retain the existing explicit successful-flow semantics and do not reset unrelated policies/dimensions or durable proof/account limits.

CounterDecision/CooldownDecision now explicitly carry availability. Every admission caller uses CanAdmit, which excludes unavailable replies even if an erroneous allow bit is present. Cooldown BlocksAdmission includes unavailable status. Infrastructure timeout/unavailable reason codes remain distinct from limit/proof denial; cache and PostgreSQL failure metrics use fixed dependency labels and contain no identity/credential/error values. No SQL budget rows are proof attempts or security-operation receipts.

## Provisioning, cleanup and transitions

1. Use the current direct greenfield setup, including the budget table/four versioned functions, before enabling the new mode. Existing setup 001 is edited and checksummed directly; setup 002–006 and all prior 172 function definitions remain unchanged. No new deployed upgrade/backfill/migration sequence or compatibility alias is introduced.
2. Select Login and/or Delivery explicitly and keep PostgreSQL available even during healthy cache periods. `PostgreSqlBudgetTimeoutMilliseconds` defaults to 1000, range 50–5000. SQL lock waits are additionally limited to min(250ms, half that budget). Cache timing remains independent; this PR does not establish a total multi-gate endpoint deadline.
3. Keep unsupported policies in FailClosed behavior. If the selected SQL owner is missing, unhealthy or uncertain, deny instead of treating an existing account/proof row as fallback. Remote provider health and explicit emergency stops remain independent.
4. PostgreSqlAbuseBudgetCleanupWorker runs only in selected version-1 mode and honors existing RetentionSettings.Enabled, PollSeconds, BatchSize (at most 100) and DryRun. Both dry-run observation and deletion skip locked rows and visit only expired retention intervals; active windows/cooldowns are preserved. Defaults keep DryRun=true. Enable actual expiry deletion deliberately after inspecting observations; disabled/dry cleanup retains expired rows and requires capacity monitoring. Cleanup affects no live proof/account/outbox data.
5. Start the chosen mode with a fresh greenfield deployment. Runtime mode/policy changes require restart and must not mix replicas with different authority selections while requests are admitted. For later operational switches, quiesce affected work and preserve enforced budgets, or leave affected admission disabled until previous maximum window plus cooldown has elapsed (48 hours conservatively under supported bounds). Returning to FailClosed while outage-period durable history is active and sparse Redis history is healthy could discard the stronger budget; it is not a safe live rollback. Rollback must retain the budget owner/enforcement or keep admission disabled through the interval. No live history-copy/backfill/compatibility mechanism is claimed.

## Validation and qualification limits

Nineteen new Python source mutation checks witness selection, SQL-before-cache, unavailable guards, exact expiry/upsert/clock, bounded cleanup, startup rejection and mandatory native collection. They are supplemental structure checks. The full tooling suite contains 267 tests.

Twenty-five native methods (64 inline-expanded cases) are authored: real host supported/unsupported/default configuration; selected/unselected/Redis-only matrices; SQL-first healthy-cache ordering; SQL failure/limit denial, missing owner, timeout/late completion, cancellation and snapshot fences; reset/cooldown rules; actual Login and TwoFactor delivery entry points rejecting work; real PostgreSQL plus independent cache connections and 64-way threshold races across all six pairs; healthy/outage/recovery shared history; observed real SQL lock timeout and clock-after-lock window rollover; isolated reset, bounded locked-row/dry cleanup and unsupported SQL input allocation denial. The SQL/cache cases are mandatory in the native SQL harness and must run with both supported cache fixture products. Host fixtures retain real Program/options startup while removing hosted workers and substituting the SQL budget interface; they do not qualify worker lifecycle.

Native compilation, application/cache/PostgreSQL execution and PowerShell are Blocked/NotRun here: .NET SDK, PostgreSQL client/server, Docker/cache services and PowerShell are absent. Source checks cannot prove atomicity, plans, performance, runtime behavior or qualification. Preserve all release gates Open. Database catalog parity, durable contention, query plans and provider/hash denial must be measured in the native environment.
